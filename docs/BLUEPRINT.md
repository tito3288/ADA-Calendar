- September 8 ongoing-project decision: the owner may leave total and remaining effort unknown while booking explicitly dated work sessions. Only those sessions reserve time; their duration is not the project estimate and cannot predict a project finish. Unknown-total reservations must not be silently lost during replanning. - Voice/typing share one validated command path. Multiple tasks may be entered together. Client aliases ground matching. Ambiguous dates, names, effort, and intent require clarification before dependent writes.
- September 8 selected-date decision: Month view has an explicit Select dates mode. One click selects a day; the second selects an inclusive range, including across months. Normal day navigation is unchanged outside that mode. Ask ADA receives typed date context for one instruction and retains it through private clarification replies, with Change/Clear controls. ## September 9: Find a time for me

- New manual work defaults to **Find a time for me**: choose one day or an inclusive range, plus total hours or hours each configured working day. **Choose exact times** remains available.
- Calendar date selection also offers **Add work on these dates** (or **Request work on these dates**). The manual form starts with the selected day or inclusive work window; hours default to a total, not a daily repeat. Cancel keeps the selection, and successful booking clears it. Display-only timelines stay separate: use Ask ADA for those, or switch to Work window before booking hours manually. No assistant call is needed for the manual path.
- Existing projects expose **Find a time for me**, and Edit work offers the same shortcut. The owner can book additional hours without changing the project estimate or display span. Unknown totals remain unknown. Waiting projects resume only with explicit booking authorization; manual previews show that choice before confirmation.
- Smart fit appends reservations through the shared scheduler. It never moves existing sessions, uses protected/reserve time, or silently books outside the requested range. A failed fit is all-or-nothing. Work hours, lunch, unavailable blocks, elapsed time, focus minimums, allowed dates, daily quotas and firm deadlines remain authoritative.
- Known projects may reserve only their unreserved remaining effort; increasing the estimate is a separate explicit edit. A partial booking does not imply a project finish. New daily requests persist their daily quotas. Existing daily plans are not silently redistributed by an add-time request.
- Typing and voice use the same grounded path: “Find time for 2 hours today for Oil Survey system” adds only that booking. The model supplies intent, not clock-slot authority. Failed fits retain private clarification context, so “Try tomorrow” can continue with the same project and hours. Explicit clock ranges still use exact-session validation.
- Manual changes are previewed and confirmed. Clear authorized Ask ADA instructions retain the existing automatic-save behavior. Requesters may smart-fit new estimated work only; they cannot add hours to existing projects. Preview version/fingerprint checks, server revalidation, atomic persistence and idempotency apply unchanged. No new database fields or migration are required.

## September 9: ADA workspace helper

- A separate floating **ADA** button opens a keyboard-accessible corner chat on desktop and a screen-fitting panel on mobile. It remains available across workspace pages. The existing **Select dates → Ask ADA / Add work** creation flow is unchanged.
- This helper answers questions about saved work, daily agendas, weekly booking totals, visible requests and the owner's saved private notes. Notes and pending requests are not scheduled tasks and are not counted as reserved hours. Unbooked daily/weekly capacity means whole-day/week booking totals, not usable time remaining after the clock has advanced. Answers identify their saved sources and snapshot time; bounded excerpts must not be presented as complete records.
- The owner can **rearrange existing sessions on one day**, shorten/increase a booking, add hours to an existing project on a day or within a range, move a booking to another day or clock time, and transfer part of a booking to another day. It cannot create projects, delete or complete work, edit notes or project details, or change effort estimates. Requesters can ask questions but cannot edit existing work; viewers continue using the calendar directly. Private notes and conversation history never enter shared AppState or another actor's context.
- The helper proposes intent, not clock authority. Names/aliases, source/destination dates and hour amounts are grounded against the current instruction and existing work. Ambiguous bookings or conflicting instructions require clarification. The shared scheduler preserves whole-booking IDs, other dates and unselected sessions, avoids lunch/meetings, and honors availability, allowed work dates, earliest starts, deadlines, daily quotas and protected-time rules. Started and historical sessions stay unchanged. A failed fit changes nothing; it does not displace unrelated work or silently extend project boundaries. Protected edits require fresh explicit owner permission.
- Booked hours and remaining effort are separate. Resizing or transferring a booking never changes the project estimate; unknown totals remain unknown. Extra bookings cannot exceed known unreserved remaining effort. Explicit shorter bookings may carry an owner-authorized per-session focus exception, without lowering the project's usual focus minimum. Daily quota adjustments are limited to the requested booking changes. A direct booking request can resume waiting work, but the preview must disclose that status change; asking to keep it waiting does not authorize executable sessions.
- Every change requires a before/after preview and an explicit **Confirm new order** or **Confirm schedule changes** click. Booking previews show dates, clock times, durations, hours freed/added, resulting daily availability and any status/quota/focus changes. Questions, speech transcription, closing the chat, selecting a day and discarding a preview never mutate the calendar. Confirmation accepts only the actor-private cached command, rechecks current authorization/version/clock/fingerprint, and uses the normal atomic/idempotent commit and notification path. Stale previews require renewed review; no automatic retry with changed times.
- The owner sees a persistent **Undo last change** card for their latest saved helper change, including after closing/reopening the chat or refreshing. This deterministic action uses the existing authorized, version-aware undo transaction, not an AI command. It restores the previous bookings and project details only while that exact event is still the latest unchanged schedule version. Undo cannot remove or alter already-started work or restore a booking into the past; shared server checks and the database transaction enforce both directions. Private notes remain untouched. Pending previews and unsent drafts block undo rather than being discarded. An uncertain response is reconciled by reading the saved event before any retry, never by targeting a newer change. Undo is a single eligible rollback, not unlimited history; it creates the normal corrective event/notification and cannot recall sent email.
- Chat uses a separate server endpoint and namespaced bounded private history, without consuming or changing a pending task-creation clarification. Saved documents, request text, old assistant answers and notes are reference material, not permission to act. The model/provider and usage limits remain unchanged. Local tests disable live AI and email. Session focus exceptions persist in existing JSON bodies, with a database migration enforcing their validation and owner-only authorization at the transaction boundary.

## Architecture contract

`src/lib/types.ts` defines WorkCommand, ScheduleSnapshot, ScheduleProposal, WorkEvent and AppState. Pure TypeScript scheduling is independent of providers. Model tools propose domain commands, never raw database/email operations. All mutation paths revalidate authorization, schedule version and constraints.

Persist committed changes, immutable event and per-recipient notification jobs in one database transaction. Prevent overlap and concurrent stale commits. Retry using stable operation/event IDs. Recompute stale previews; never turn a stale clean-fit request into an authorized displacement. Undo is a version-aware compensating change.

Supabase Queues and Cron run bounded mail workers independently of the browser. Track provider IDs, retries, failures and uncertain outcomes. Resend idempotency lasts 24h; uncertain older sends require reconciliation. Verify webhook signatures and handle repeated/out-of-order callbacks. Keep production credentials server-side.

OpenAI Responses model `gpt-5.6-sol`, medium reasoning, strict schema; `gpt-transcribe` recorded speech. Warn at $20 monthly usage and pause new AI calls at $25 until owner raises allowance. Manual operations remain available. Approximate total operating target $100; Railway is usage-priced, so report observed costs, not a guaranteed fixed total.
